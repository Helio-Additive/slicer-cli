# libslic3r-rs Parity Roadmap

**Goal:** make `crates/libslic3r-rs` an exact, file-by-file 1:1 port of
`libslic3r/bambustudio/references/BambuStudio/src/libslic3r`, usable as a drop-in
library inside the CLI (replacing the C++ slicer subprocess) **and** compilable to
`wasm32` for the browser — no dynamic links to system packages/dylibs; upstream
native functionality replicated by minimal vendored Rust crates scoped to only the
functions actually used. Success = byte-identical G-code on the integration tests.

## ⚠️ Biggest risk to exact parity (read this first)

The biggest risk to EXACT gcode parity is that the map almost certainly overstates completeness 
because the crate ships two parallel module trees and ~70 modules (including core slicing/path 
files PrintObjectSlice, ShortestPath, FlushVolCalc/FlushVolPredictor, OverhangDetector, the entire 
SLA subtree, and the flat Point/Polygon/ExPolygon/ExtrusionEntityCollection set) are explicit 
auto-generated 'Stub placeholder - implementation needed' files still pub-exported from lib.rs. The 
reported 'orphans' list is unreliable: most entries are not orphans but the redundant/competing 
half of a flat-vs-hierarchical duplicate pair, masking which implementation is authoritative. Most 
dangerously, the executing gcode emitter is gcode::exporter (a 3085-line orphan with no C++ source 
mapping) invoked by Print::export_gcode, while gcode/generator.rs (the file that would be mapped to 
GCode.cpp) is dead/unreferenced and gcode/reader.rs is a 19-line stub shadowing the real 1081-line 
gcode_reader.rs. Because exact byte-for-byte gcode depends on toolpath ordering (ShortestPath - 
stubbed), seam placement, flush/purge volumes (FlushVolCalc - stubbed), cooling/pressure-equalizer, 
arc-fitting and placeholder-parser interactions, and the live emitter is an unmapped 
reimplementation rather than a verified port of GCode.cpp/GCodeWriter.cpp, parity cannot be assured 
from the current map. Priority-weighted real completeness is ~45 percent: 
geometry/perimeter/surface/fill/arachne/support hierarchical trees are substantively implemented 
(1000-3000 line files), but the gcode-determining tail and many 1:1 'done' records resolve to stubs 
or to a parallel emitter the map does not track. Recommended next steps: (1) collapse the duplicate 
trees and mark which module is authoritative per C++ file; (2) re-classify every file whose Rust 
target contains the stub banner as missing/partial; (3) re-key the GCode.cpp/GCodeWriter.cpp 
records onto gcode::exporter and audit it line-by-line, since it is the only path that actually 
produces output.

## Recommended sequence

The map says the geometry/perimeter/fill/arachne/support trees are substantively
implemented, but the **G-code-determining tail is stubbed or unmapped**. Do this in order:

1. **Collapse the duplicate module trees.** The crate ships a flat set
   (`point.rs`, `polygon.rs`, `expolygon.rs`, `extrusion_entity_collection.rs`, …)
   *and* a hierarchical one (`geometry/…`). Pick the authoritative module per C++ file,
   delete/redirect the other, and fix `lib.rs` exports. Until this is done, "done"
   counts are unreliable.
2. **Re-key the G-code emitter.** `Print::export_gcode` runs `gcode::exporter`
   (3085 LOC, no C++ mapping) while `gcode/generator.rs` (the real `GCode.cpp` target)
   is dead and `gcode/reader.rs` (19 LOC) shadows the real `gcode_reader.rs` (1081 LOC).
   Decide whether `gcode::exporter` *is* the port of `GCode.cpp`/`GCodeWriter.cpp` and
   audit it line-by-line, or replace it with a faithful port. This file alone decides parity.
3. **Re-classify every Rust file containing the `Stub placeholder - implementation needed`
   banner as `missing`/`partial`** (re-run MAP after step 1 to refresh).
4. **Stand up the vendored micro-crates the critical path needs** (see table): `clipperish`
   (replace the two wasm-breaking clipper crates), the `exec-shim` for tbb→rayon with a
   single-thread wasm fallback, then `its-mesh`, `cdt2d`, and `convexhull3d` as the slicer
   reaches them.
5. **Port the critical-path files** (top table), each via the workflow PORT phase:
   faithful 1:1 translate → adversarial fidelity review vs C++ → `devbox run cargo build` gate.
6. **Gate on G-code parity** with the VERIFY phase after each batch; every first-divergence
   becomes the next PORT work item.

## Hang fix — slicer now runs end-to-end (2026-05-30)

Found via the `libslic3r-fix-perimeter-hang` workflow (runtime marker-bisection + static loop hunt). **The crate compiled but hung on a 12-triangle cube**, blocking all G-code parity measurement.

**Root cause:** unit-mismatch bug in `Print::_make_skirt` (`print.rs:~1335`), *not* perimeters/Arachne (those + infill/ironing/support complete fine for 128 layers). `_make_skirt` passed the offset delta in **scaled** units (mm × 100 000 via `scale()`) to `clipper_utils::offset_polygons`, which expects **mm** (it unscales coordinates internally). The sibling `make_brim` in the same file already passed mm correctly — the decisive proof it was the call site, not the helper or the clipper crate.

**Fix:** 3 lines in `_make_skirt` — pass `skirt_distance` and per-loop `nozzle_diameter * i` in mm instead of `scale(...)`. Faithful to C++ `Print.cpp::_make_skirt` (where coords *and* delta are both scaled; the Rust port unscales coords in `clipper_utils`, so the delta must be mm). Build exit 0; only `print.rs` changed.

## Config-hierarchy threading — WIRED (2026-06-12, steps 1–8)

The Print→PrintObject→Layer→LayerRegion config hierarchy is now wired with
Arc-distributed config snapshots over the existing downward ownership tree.
**This is the canonical C++ mapping going forward:**

| C++ accessor chain | Rust equivalent |
|---|---|
| `this->layer()->object()->print()->config().first_layer_height` | `layer.object().print().config().first_layer_height` |
| `this->object()->config()` | `layer.object().config()` |
| `layerm->region().config().wall_loops` | `layer_region.region().config().wall_loops` |

Mechanics (do not relitigate): `Print::print_regions` is `Vec<Arc<PrintRegion>>`
shared (same Arcs) into `PrintObjectRegions::all_regions`; `PrintObject` holds
`print_config: Arc<PrintConfig>`; `Layer` holds `object_config` + `print_config`
Arcs; `LayerRegion` holds `region: Arc<PrintRegion>` + both config Arcs.
Zero-cost view structs `PrintRef<'_>`/`ObjectRef<'_>` (`print_object.rs:149/169`)
preserve the C++ call shape. Arcs are stamped at sync points
(`Print::add_object`, top of `Print::process`, `wire_config_hierarchy` /
`wire_layer_hierarchy` at slice/step entries) — faithful because C++ configs
only mutate inside `Print::apply` and any diff invalidates `posSlice`.
**INVARIANT:** always replace Arcs wholesale (clear + `Arc::new`), never
`Arc::make_mut`/`get_mut` — forking the share silently breaks identity.
