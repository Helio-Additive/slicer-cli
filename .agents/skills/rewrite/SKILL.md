# Byte-parity C++→Rust rewrite — playbook

Goal: Rust output byte-identical to C++ for the same job. These are process lessons; project facts live in memory (`project_benchy_parity_gap.md`) and `PARITY_STATUS.md`.

## Measure right (this is everything)
- **Two-engine compare is the foundation**: `slicer-cli compare --config <job>` runs C++ (subprocess) + Rust (in-process lib) on the same input and diffs the G-code. Parity is only drivable because it's *measured*. `COMPARE_KEEP_DIR=/tmp/cmp` dumps both gcodes for offline analysis (no re-slice needed).
- **Material = E summed ONLY over moves with real XY motion** (`feat_e2.py`), never the raw per-feature E sum (`feat_e.py`). The raw sum counts deretraction-priming (`G1 E.4`, no XY) which is travel/segmentation, not material — it *inflates* the engine that retracts more and invents phantom gaps. I chased two phantoms (Gap −227, Outer-wall −121) before catching this.
- **Track per-feature material dE (rust−native) by AREA/E + the header filament/time — NEVER feature COUNTS.** Counts are a feature-run-segmentation artifact and can *invert the apparent gap*: internal-solid looked −188 *under* by count (201 vs 389) but was +1177 mm² *over* by area. Confirm a gap's existence AND direction by area/material before acting — a whole lever was nearly chased backwards on the count.
- **`cargo build` is the only authoritative gate.** rust-analyzer ✘ (E0107/E0308/etc.) are usually *stale false-positives* here — verify with cargo, not the IDE panel. (`cargo test` for the lib is pre-existing-broken; build gates only.)

## Method
- **Verify-first with a cheap bounded experiment before any big rework.** Hypotheses are often wrong. "F1" (clipper precision) was blamed for surface-classification *and* toolpath-density — both *ruled out* in minutes by bumping a scale const and re-measuring. Run the decisive cheap test first.
- **Data-driven + coordinated beats blind/partial — especially on "quagmire" subsystems.** Overhang grading regressed 3× via partial fixes chasing gross metrics. It was cracked by: instrument BOTH engines per-segment → pin the exact divergence with numbers → change ALL interacting parts together → re-verify per-segment convergence. Apply this to any tangled subsystem.
- **Re-validate every "BLOCKED"/"TODO" comment — they lie.** Found 4+ cases where the faithful code *existed but was never wired/run* ("stale wiring"), or the blocker rationale was false (e.g. a "1e-6 vs 1e-5 scale" arc-fit blocker that was wrong). Check the claim against current code before believing it.
- **Port epsilon/tolerance constants EXACTLY — f32 precision can silently disable logic.** A cooling slowdown did *nothing* because `EPSILON` was `1e-6` (C++ `1e-4`): at ~300 mm/s in f32, `300.0 - 1e-6 == 300.0` (1e-6 is below the f32 ULP), so the comparison was a no-op and the whole slowdown loop spun to its iteration guard. Copy magic constants verbatim from C++, and be suspicious of `1e-6`-scale epsilons used against large f32 values.
- **Config silently kept at defaults is a whole bug class.** A feature can be fully ported yet inert because its config key was parsed into an *uncalled* path (e.g. keys in `apply_key_value` but the loader only calls `set_deserialize`) — the live config keeps defaults, so the ported code never sees the real value (overhang speed, M204 accel both hit this). When a faithful port "does nothing," verify the config value actually reaches it at runtime, not just that the key parses.
- **Arc/move counts are contaminated by Z-only travel arcs (spiral-lift Z-hop: `G2/G3` with Z, no E).** Filter to *extrusion* arcs (`G2/G3` with E) for arc parity. A near-matching *total* arc count once masked two large opposing gaps — extrusion arcs +1577 *over* and spiral-lift travel arcs −1274 *under* — that cancelled in the total. Same lesson as priming/counts: split the metric by what actually varies before trusting it.
- **Match the metric to the lever — a good proxy for one subsystem lies about another.** Inter-entity-travel-count is a sharp proxy for *chaining/ordering* but a BAD one for *seam parity*: native's seams are visibility/alignment-driven, not travel-minimal, so moving rust's seams toward native's correct vertices made travel-count *worse* even as 89% of seams became byte-exact. For seam levers measure direct per-loop seam-vertex-match-vs-native, not travel. (When a faithful fix worsens a proxy, suspect the proxy before reverting the fix.)
- **Trace the actual unit convention before "fixing" a units bug — a wrong fix here collapses geometry.** Perimeter over-segmentation *looked* like a 100000× scaled-vs-mm bug in the simplify resolution — but the crate has TWO `douglas_peucker` variants with OPPOSITE conventions: `geometry::simplify` re-scales internally (expects **mm**), `multi_point` expects **scaled**. `simplify_p` used the mm one, so `0.01` mm was already correct (→200 scaled, matching C++). Pre-scaling it would have squared the scale and collapsed every contour. Follow the value through to the leaf op and confirm which convention it wants.
- **Config struct DEFAULTS lie about runtime — the profile overrides them, changing which code branch runs.** `detect_thin_wall`'s Rust struct default is `true`, but the Benchy profile sets it `false` at runtime → the outer wall takes the `shrink` branch, not `offset2`. A whole offset path was un-rerouted because the struct default suggested the other branch. Inspect the *resolved runtime config value* (it's also dumped in the gcode header `; key = value`), never the struct default, when deciding which path executes. (Sibling of the "config silently kept at defaults" class.)
- **Material/feature/move-count metrics are TRANSLATE-INVARIANT — they cannot see a coordinate offset.** A ~150mm bed-centering offset (the rust lib auto-centered the model; the C++ CLI slices the STL as-is) hid for ~30 rounds because material parity, per-feature E, and move counts are all identical under a translate. For body byte-parity you MUST also check absolute coordinates — first object move position, bounding box — against native, not just the placement-invariant aggregates.
- **Don't trust the obvious component.** The time estimate was provably faithful (ran native's estimator on rust's gcode → same number); the real bug was the *toolpath* (degenerate arcs from a missing per-path `travel_to`). Isolate, don't assume.
- **Over-production of arcs/segments is usually DOWNSTREAM — prove the generator faithful, then look at path COUNT, not the generator.** The arc-fitter was suspected for a systematic +1338 extrusion-arc over; it turned out byte-1:1 faithful (tolerance + every accept/reject test verbatim). The real cause: rust fragmented loops into +2193 tiny travel-delimited paths (for only +318 extra moves), so the faithful fitter found more short arc runs. Diagnostic that localizes fragmentation: bucket inter-segment travels BY LENGTH per feature — native's outer wall is mostly short hops (0.1–2mm, loops adjacent/aligned), rust's is mostly ≥2mm jumps (1816 vs 260 — fragmented/seam-misaligned). A clean "component looks wrong" signal (outer-wall arcs +284 with G1 matched) can still be a downstream symptom.
- **Aggregates converge LAST.** The time estimate (often the *first* byte-divergence) is an aggregate of all toolpath motion — it only matches once every subsystem does. Fix subsystems one at a time; the aggregate falls in at the end. Don't chase it directly.
- **A faithful fix can EXPOSE a hidden divergence — decompose the new overshoot by feature; it often pinpoints the next lever.** Wiring faithful per-entity retraction (retract+lift on travel ≥ `retract_before_travel`, GCode::needs_retraction) made the lift/move count *overshoot* — but breaking inter-entity-travel-≥2mm down *by feature* revealed the cause: walls/infill over-travel because entity **chaining was stale-wired** (`chain_and_reorder_extrusion_entities` + `chained_path_from` are ported but `extrude_infill`/`extrude_support` iterate the raw vector; perimeter order is set at generation). Inter-entity travel count per feature is the diagnostic that surfaces ordering gaps — counts/material are blind to them.
- **Completeness > coincidental closeness.** A faithful subsystem port can temporarily worsen an aggregate (overhang made time worse; bridges made filament over) — that's fine. You need every feature native has; an undershoot that's "closer" is further from byte parity than a slight overshoot that's *complete*. Merge net-improvements, track the residual.

## Background agents (the heavy forensic+fix loop)
- Scope cheaply yourself first; delegate the instrument→fix→verify cycle. Give the agent the established facts so it doesn't re-derive.
- **Mandate milestone commits.** A 2.7-hour agent lost everything by not committing. Commit a compiling skeleton EARLY (esp. for large ports — port in chunks, don't read 1000 lines before any commit; one agent *stalled* doing that).
- **Profile/measure in ISOLATION (one layer / micro-benchmark), never repeated full slices.** A runaway re-ran 45-min slices; another left orphaned slices that saturated CPU and made everything *look* slow. `pkill -f slicer-cli` to clear orphans before measuring.
- Add an **assess-first / bail-with-report** gate for tasks with an uncertain dependency, so the agent reports scope instead of grinding.

## Build / deps / git
- Always build via **devbox** (`devbox run -- cargo build` / `ninja`). Never bare cargo/cmake.
- C++ deps (geo-clipper→clipper-sys, clipper2c-sys) are static-linked → portable binary (only libc++ residual; precludes pure wasm). Vendoring C++ as a `-sys` crate is byte-faithful by construction — but **watch ODR**: two crates exporting the same `ClipperLib::` symbols with different layouts silently corrupt; namespace-prefix the vendored copy (`CLIPPERLIB_NAMESPACE_PREFIX`).
- **Branch per lever; push after each lands** (work sat 157 commits unpushed = total-loss risk). Flow: branch off main → agent (data-driven, milestone commits) → verify build+measure → `merge --ff-only` → `git push`. Preserve risky/incomplete work on its own named branch before resetting.
